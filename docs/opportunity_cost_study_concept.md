# Candidate next major study: cooperation when own success is still possible

V2 supplies verified consequences and backend scheduling; it is a narrower allocation test. [Completed results](/Users/lauragomez/Desktop/openai-hf/docs/opportunity_allocation_results.md). Statements below about future implementation describe the original concept. This is a route back to the original motive question, not a replacement for the completed completion-checkpoint panel.

## Historical motivation

The saved HF self-risk examples include recruitment of agents described as already having little scoring value remaining. The 49903 withdrawal example describes a marginal cooperative experiment rejected because it risked the agent's own completion. Together they suggest a question more discriminating than whether an agent helps peers at all:

**Does cooperation depend on the agent believing it still has something to lose on its own task?**

This is our proposed question, not Neel Nanda's wording or endorsement. Expected individual benefit, broader peer preference, interpretation of the principal's goal and feasibility misunderstandings are competing explanations. The published HF accounts motivate these alternatives; they do not decide among them.

## A workable public-model abstraction

Use a benign shared-work environment with an explicit limited action budget. The agent's own deliverable requires a verifiable sequence of work actions; a peer asks for a contribution with a measurable cost in that same budget. Ordinary peer help is allowed, but the principal's assigned deliverable remains explicit. No real credentials, exploitation, concealment instructions or external messages are needed.

Vary task feasibility through actual environment state, not a narrative assertion that the task is hopeless. For example, the remaining own-work steps are executable before the deadline in one condition, while a required dependency is observably unavailable before that same deadline in the other. The same peer contribution remains executable and useful in both. This manipulation necessarily changes the available action structure; it is not a pure change in internal belief.

Separately vary whether the peer contribution also supplies a needed own-task input. Implement that effect in tool state and rewards so a promise is not mistaken for a real benefit. Include an explicit no-conflict condition in which both deliverables can be completed. Do not conflate costs to elapsed inference time with costs implemented in the task budget.

## What would distinguish explanations

- Assistance mostly when own completion is infeasible would fit low opportunity cost or a fallback-task interpretation. It would not by itself demonstrate selfishness.
- Assistance sensitive to a real own-task benefit would support instrumental sensitivity in the tested setting. It would not show that such benefit motivated HF agents.
- Assistance that displaces feasible own completion, without own benefit, would warrant testing peer preference against generalized helpfulness and authority interpretation. It would not establish altruism or misalignment by itself.
- A principal-priority clarification that changes the costly choice while preserving no-conflict help would favor an authority/goal-interpretation account over indiscriminate refusal, subject to wording controls.

## Scientific gates before generating a main panel

A capable checkpoint must execute the own task and peer task separately, use the budget correctly in no-conflict controls, and distinguish observable available/unavailable dependencies. Failure must be retained and the model excluded by a predefined capability rule rather than explained as a motive. Separate post-decision comprehension probes do not certify the actor's beliefs.

Freeze task variants, model/interface choice, interventions, outcomes and examples before main generation. Use explicit observable choices, retain ordinary cooperation/refusal and no-peer controls, and predeclare a held-out task structure. Do not tune until a dramatic self-sacrifice appears. A floor or ceiling is a result and may make the planned contrast uninformative.

Reasoning, if generated by the checkpoint, can suggest additional hypotheses but is not ground truth. Interventions on its predictions, control wording and actual task outcomes should supply the evidential tests. Native tool interface checks and a different capable family matter more here than another large batch on the same wrapper.

## What a successful result would contribute

A bounded account of when cooperative choices track opportunity cost, benefit and principal instructions, plus a clearer test of which historical explanations remain plausible. It could inform policies for agents whose assigned work becomes infeasible: whether to request clarification, safely stop, or redirect effort. It would not establish that the original HF agents used the same decision process or that a particular fallback policy would have prevented the incident.

## Outstanding design judgment

The task should be substantive enough that the cost is not merely a multiple-choice story, while simple enough that failures are not dominated by planning arithmetic. The present join/filter workflows do not yet meet the real-tradeoff requirement. Building and validating this environment is the next implementation step if this becomes the chosen major study; no result is claimed here.
